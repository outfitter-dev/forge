## Supported events and their distinct subjects

| Surface | Supported behavior | What it does not establish |
| --- | --- | --- |
| GitHub Actions | [`merge_group` with `checks_requested`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group) runs against the integration SHA/ref. It is separate from PR and push triggers. | A candidate build is not fresh verification, agent review, or human approval of each member PR's exact head/base. |
| Buildkite merge queues | [Build merge queues](https://buildkite.com/docs/pipelines/tutorials/github-merge-queue) consumes merge-group events instead of ordinary pushes to temporary `gh-readonly-queue/*` branches. | Existence of a temporary branch does not prove a merge-queue build with bound queue metadata or fresh member admissions. |
| Buildkite variables | Candidate head/ref are `BUILDKITE_COMMIT`/`BUILDKITE_BRANCH`; base/ref are `BUILDKITE_MERGE_QUEUE_BASE_COMMIT`/`BUILDKITE_MERGE_QUEUE_BASE_BRANCH`. | These are candidate identities, not a complete list of PR members or their individual bases. |
| Invalidated groups | Buildkite can [cancel destroyed-group builds](https://buildkite.com/docs/pipelines/tutorials/github-merge-queue#automatic-cancellation-of-redundant-builds) when that setting is enabled. | Cancellation is not a clean result or evidence that a replacement build/member review completed. |
| PR updates | [Buildkite's GitHub integration](https://buildkite.com/docs/pipelines/source-control/github#running-builds-on-pull-requests) documents PR open/update, same-repository push, fork synchronize, and optional edit/base-branch-change, review-request, and dequeue triggers. Duplicate-build skipping can depend on commit/branch. | Moving a target branch's tip is not necessarily editing a PR's target branch name or pushing its head. These docs do not prove that every unchanged-head independent PR is requalified on a new base. |

GitHub's [merge queue guide](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) describes speculative groups that incorporate earlier entries. Build concurrency controls requests for checks; merge-size limits affect landing and do not combine the merge-group builds. Do not infer that two PRs merged together had identical group heads or one combined build. Capture actual events, API snapshots and candidate ancestry before claiming a mapping.

## Pilot mapping and fail-closed limits

Inspected source is local pilot HEAD `897810f03bc14098809c5a113472649923d0d905`. GitHub's qualified `5264279b9ce776d2a8f8e6c3785c663d9b653cf8` has the same `machinery/merge_queue.py` blob (`5aff69924a5628c9db9442b8773830d6c5c6d9fe`). The local checkout lacks that squash object; comparison used read-only GitHub blob metadata, not a source checkout mutation. This is source evidence, not current service-settings evidence.

`queue_snapshot` reads the target SHA and GraphQL merge queue, requires `ALLGREEN`, and refuses a truncated snapshot beyond its 100-entry bound. `candidate_members` indexes unique candidate head commits, walks speculative base links to the target, requires the event base to match the candidate's immediate base, and verifies consecutive prefix positions and unique PR IDs. It preserves each PR's separately collected head/base/target branch; a stacked PR can have a different base from the candidate. Missing/cyclic chains, duplicate candidate heads, missing positions, branch mismatch, and repeated PRs fail closed. In particular, shared-head/batched shapes are explicitly rejected until qualified; neither this investigation nor the generic GraphQL field descriptions prove that the prefix algorithm supports all GitHub modes.

`load_admission` requires the saved repository, runtime fingerprint and exact PR head/base, then reevaluates its gates. `collect_candidate` recollects mutable PR state and queue membership and refuses movement during collection. `worker.context` pins verification head/base, while `host_worker` distinguishes candidate membership from PR evidence. The pilot does not schedule independent-PR refresh when main advances. Native-stack head updates observed in the historical run exercise a different path.

The [GraphQL reference](https://docs.github.com/en/graphql/reference/objects#mergequeueentry) defines nullable entry head/base commits and PR, position and state. It does not grant authority to parse PR membership from temporary branch text or assume a stable unique-head prefix across all configurations. Nulls, pagination gaps, service errors, unsupported strategy/group shape, stale queue snapshots and unavailable admissions must block. No replacement membership parser is implemented here.

## Offline evidence and refresh rule

[Admission-refresh regressions](../tests/admission-refresh.test.ts) exercise two independently based members with assigned approvals. With unchanged PR heads and independently collected new member bases, newly passing integration checks cannot make old admissions pass. Merely updating an admission's subject cannot relabel old verification, agent review or human approval. Complete fresh member evidence restores eligibility; a voluntary outstanding objection still blocks. A separate case preserves the distinction between candidate-base movement and independently collected member bases rather than automatically rebinding stacked members.

These tests prove evaluator handling of normalized snapshots, not event delivery, authentic collection, orchestration, provider review, human participation or live queue behavior. No production evaluator changes are necessary for these cases. Missing review or unavailable authentication remains blocked. An explicitly required Devin provider cannot be satisfied by its green status; FOR-9's findings gap remains separate.

## Bounded reproduction before choosing a mechanism

The earlier proposal used the existing disposable `outfitter-dev/agentic-ci-pilot` and its established Studio/Rex topology. Future execution host is explicit configuration; Studio is one possible host, not a permanent or sole requirement. No new host or production consumer is selected here. Recheck time-sensitive availability under the selected operations; current setup evidence is maintained in the handoff (the read-only refresh is in [Forge PR #11](https://github.com/outfitter-dev/forge/pull/11)). The native reviewer pane was observed exited at its four-hour limit; no restart is authorized by this document. No current GitHub/Buildkite setting or webhook delivery has been inspected here.

The proposed execution packet must explicitly authorize at most two harmless independent fixture PRs targeting the same disposable base, their necessary review/build/queue actions, one controlled target advancement, and cleanup. Capture current ruleset/queue settings, enabled webhook events, Buildkite PR/queue/cancellation/duplicate-skip settings, active jobs and trusted runtime/configuration before changing anything. Preserve the real assignment/admission ledger; do not waive or fabricate assigned-human approval. Name participants and permitted review-provider budget if required. Keep existing worker slots; queue build concurrency is distinct from worker capacity.

1. Qualify both PRs at known head/base/runtime, recording authentic per-member receipts and assignment/objection state. Enqueue only under explicit actor/merge authority; successful gates are not permission to land.
2. Capture event delivery IDs/payload subjects, queue snapshots before/after, Buildkite build/job identities and candidate receipts for two entries. Check mapping and stable collection windows against the actual shape. If it is unsupported or transient, block and preserve evidence rather than infer membership from names.
3. Advance the target once as authorized while retaining an independent PR head, then capture the regenerated candidate and authoritative new PR base. Confirm the old admission blocks. Determine which native events/builds actually occur, including duplicate suppression and cancellation. Obtain fresh verification, agent review and any required human approval for the new base; record exactly what restores eligibility.
4. Include an intentional failing member, missing/old-base admission and destroyed candidate. Prove a passing integration cannot bypass those blockers, and that stale/canceled work cannot qualify replacement identities. Close/dequeue only selected fixtures under cleanup authority, preserve receipts and state, and report unsupported cases.

Only after this reproduction should an implementation be selected. Prefer native event/configuration support if it establishes the required requalification. If demonstrated insufficient, propose the smallest trusted event-to-requalification operation keyed by repository/PR/head/base/runtime, with bounded duplicate handling and a fresh collection before consequential action. It must not rewrite old receipts as fresh, automatically grant human approval, change worker capacity, or become a second scheduler. The present evidence does not justify implementing such a mechanism yet.

Owner decisions before live execution are the permitted pilot branch/queue/merge operations, whether and how to restore native-review availability, required human participation, provider/build budget and time bounds, and cleanup/evidence readers. The earlier pilot host/operator was established; any future operation must identify its configured host and authority without treating this historical setup as permanent. A reviewed packet and explicit execution release are still needed; FOR-11 remains open until live two-PR and advancing-main acceptance evidence exists.

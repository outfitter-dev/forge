# Standing delivery policy examples

These examples exercise the boundaries in [AGENTS.md](../AGENTS.md#standing-delivery-authority). They are policy review cases, not executable tests or claims of deployed automation. The [automation contract](automation-contract.md) retains evidence and trust requirements; [RNG-24](https://linear.app/outfitter/issue/RNG-24) owns planning of Ranger's recovery contract.

| Situation | Expected action and owner | Boundary that must remain intact |
| --- | --- | --- |
| A scoped documentation change is ready for a PR. | The author opens a draft, runs checks, obtains independent review, repairs findings, and lands when fresh applicable evidence passes. | No per-PR permission request; a draft, stale evidence, or unresolved blocking finding is not eligible for landing. |
| A product release qualifies under its established automatic release policy and trusted setup. | The release owner proceeds within the agreed product scope using the established destination and authority. | An artifact build alone does not qualify a release. A product-required manual approval still applies; missing credentials or infrastructure route to the owner instead of being invented. |
| A review provider is unavailable. | Ranger selects another eligible independent reviewer and records coverage of the latest head and applicable base. | Provider silence or a completion-only status is not a clean review. If no eligible review completes, the gate stays non-passing with an owner and next action. |
| A failing check requires a repair that creates a new head. | The author repairs the change; Ranger coordinates fresh applicable checks and review. | The previous head's passing review cannot justify landing the new head. Recovery does not turn deterministic failure into a pass. |
| A task's agreed recovery bound is exhausted. | Ranger stops further attempts and routes evidence, reason, and next action to the accountable engineering owner; the sender retains ownership until acceptance. | Exhaustion does not waive the gate or automatically require Matt. If only Matt can resolve the next decision, the owner asks him. No universal cap is inferred from this example. |
| A task is explicitly parked, such as the tokens artifact shadow trial. | The task remains parked until its owner releases the hold. | Green checks or standing delivery authority do not restart the trial. |
| A PR carries `forge:hold`; another carries `forge:hotfix`. | The landing owner respects the hold and prioritizes the hotfix within the adopted landing path. | Neither signal bypasses required evidence, review, or product policy; this example does not configure labels or a queue. |
| Public-readiness checks pass for a private repository. | The preparation owner reports readiness; Matt is asked before visibility changes. | A readiness PR may land under routine authority while the repository remains private. |
| A scoped operation needs a new access grant or credential change. | The owner prepares the concrete need and asks Matt before changing access or credentials. | Reusing existing authorized access within its established scope does not itself request a new grant. Shared code does not share credentials. |
| A cleanup would delete a record, repository, or preserved runtime state. | The owner asks Matt before deletion. | Routine delivery does not silently remove records or preserved state. |
| An old qualification record says its run did not authorize deployment. | The documentation owner preserves that historical fact and references the standing policy for current work. | The old run proves only its recorded outcome; neither history nor the new policy establishes a deployed worker or grants privileged access to proposed code. |

The source direction's proposed recovery caps, receipt signing, queue batching, and automatic-release defaults are not adopted by these examples. Recovery bounds need a task or consumer rationale; releases retain established product policy. Forge's check implementation belongs to FOR-28, and recovery execution belongs to Ranger.

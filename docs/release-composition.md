# Offline release-assessment composition

[FOR-19](https://linear.app/outfitter/issue/FOR-19) now has an offline composition fixture in [tests/release-composition-fixtures.ts](../tests/release-composition-fixtures.ts) and [tests/release-composition.test.ts](../tests/release-composition.test.ts). It invokes existing generated-diff, strict-version, package-artifact and npm-evidence operations, then explicitly constructs named product assessments for the release-policy evaluator. All source operations and production APIs remain unchanged. The fixture-local mapping is test code, not a general orchestrator, production collector or qualified adapter.

## Explicit fictional product policy

This is read-only reconciliation of a single existing publication, using synthetic observations for `example/release-fixture`. It is not a pre-publication flow: a missing registry version cannot qualify publication or a retry. No package is published, artifact packed, consumer process executed or registry contacted by these tests. Separate artifact tests already exercise real disposable offline packages; this composition uses their normalized fixture shape.

| Assessment | Fixture policy and mapping | What remains outside the claim |
| --- | --- | --- |
| `generated-diff` | Required. Only `decision: pass` from the declared paired package/changelog and changeset-delete assessment passes. | Paths/statuses do not prove a version bump or valid changelog content. Product decides its generated paths. |
| `version` | Required. Only strict newer-version/channel success passes. | Supplied version strings need authenticated association with the actual selected package/source. |
| `artifact` | Required. Only `state: complete` from the explicit packed-artifact/consumer contract passes. | A valid JSON isolation claim does not authenticate a consumer execution or prove bytes were collected faithfully. |
| `npm-reference` | Required. Only matching package/version/tag/integrity and provenance predicate references pass. | Predicate references are not authenticated provenance; no registry transport, source attestation or publication authority is established. |
| `subject-association` | Required. Explicit fixture comparisons retain repository, diff base/head, workflow, validator, runtime, package, version/tag and artifact identity across the inputs. The captured collection selection must match the release subject. | Synthetic attribution is not a producer-authentication contract. A real trusted collector must independently establish each relationship; merely supplying matching strings is insufficient. |
| `product-intent` | Auto-only in this fictional product. Core changes map to their corresponding label; the product explicitly maps prerelease advancement/finalization to patch intent. A mismatch routes auto intent to manual. | This mapping is a product choice, not Forge's universal release intent. Moving this assessment to required checks makes the same mismatch block manual too. |

The composition returns all original operation decisions/reasons alongside normalized evidence. It conservatively maps npm `complete` to release-policy `complete`, `conflict` to `conflict`, `incomplete` to `partial`, and `invalid`/`unavailable` to `unavailable`. In this reconciliation fixture, `partial` means the desired metadata qualification is incomplete; it does not assert that some package was published. The original npm state/reasons remain available, so invalid input is not mistaken for a transport error, nor missing metadata for an unoccupied immutable version. This one-package fixture does not qualify coordinated package-set completeness or recovery.

A healthy fixture reaches auto eligibility (or manual eligibility under explicit manual intent). Unexpected edits, malformed versions, canceled artifact checks, incomplete collection, stale CI and non-complete npm evidence block both paths. Passing decisions for another repository/package or another head/base/runtime/validator/workflow cannot be relabeled as this subject. A required unsupported `authenticated-provenance` check blocks even when every reference-only npm check is complete. An old outer release evidence envelope remains stale.

These tests prove how existing contracts can be composed under one explicit policy. They do not prove a producer's identity, collection completeness, installed approval/permission controls, approval completion, a live consumer or a release action. Literal version bindings are not revision receipts; artifact bindings and diff bindings retain their own field meanings. Proposed code cannot supply trusted policy or orchestrate its own acceptance.

Run `bun install --frozen-lockfile` and `bun run check`. No live provider, publisher, credentials, workers, public adapter, product migration or new runtime framework is included.

## Minimum remaining for a real consumer trial

Stop expanding standalone pure helpers without a concrete consumer need. The next useful increment is a bounded, read-only consumer trial of the existing operations. A broader monorepo adapter or product-workflow implementation has not been released. Existing disposable `outfitter-dev` distribution pilots establish same-owner access evidence only; they are not qualification of monorepo release policy or cross-owner access.

[The qualification record](tokens-shadow-qualification.md) documents the isolation preflight abort and scoped diagnosis; no product snapshot, pack or consumer probe ran. That trial-specific selection does not release public-adapter adoption, migration or publication.

Start with one dependency-free library supported by the current artifact contract; packages with runtime/peer dependencies, binaries, export patterns or fallback arrays require concrete contract qualification first. Product-owned MONO-83 choices cannot be silently resolved here.
2. **Implement only the trusted collection needed for that package.** Select immutable workflow, validator and product source/base revisions; independently collect complete name-status diffs and actual before/after manifest versions. Bind staged tarball bytes/files/manifest and real clean-consumer results to that subject/contract/runtime, with cleanup and isolation established by the execution host. Implement explicit identity joins rather than copying a current subject onto unbound results. Preserve incomplete/unsupported evidence and diagnostics.
3. **Use a pinned invocation with existing scoped access.** The first trial can execute from an approved trusted Studio process outside the proposed checkout, fetching private Forge by immutable SHA with existing access and invoking product-declared tasks without privileged proposal credentials. This is a proposed placement, not an executed trial or authorization to start workers. If a public Actions adapter is selected instead, FOR-20 baseline health, its actual immutable code/runtime/bundle checks and private-source access must qualify before use; a public wrapper does not grant private Forge access.
4. **Separate qualification phases and authority.** First prove local pre-publication artifact/diff/version safety without registry mutation. Reconcile an already published version only through an explicitly scoped trusted read-only metadata collector, preserving FOR-18's reference-only provenance limits. If the product requires authenticated provenance, supply an actual supported verifier or keep that requirement unsupported. Missing metadata never authorizes publishing. Publish/tag/release mutation and protected approvals remain separate decisions.

Retain sanitized subject/contract/policy/run identities, reasons and cleanup evidence. Keep the old product workflow operational; shadow trial success alone does not authorize migration, publication, adapter retirement or broader access.

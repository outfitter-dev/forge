# Assigned-human approval qualification brief

This is the brief-only deliverable for [FOR-17](https://linear.app/outfitter/issue/FOR-17). It proposes an executable disposable qualification, records the human/access decisions needed before execution, and authorizes no live operations. No consumer, qualification review/approval, service configuration, or credential was created or changed to prepare it. It is independent of Ranger execution and does not expand FOR-6, FOR-9, or FOR-11.

[FOR-2](https://linear.app/outfitter/issue/FOR-2) supplies the [deterministic policy and collector obligations](evidence-evaluator.md#trusted-collector-responsibilities). [FOR-10](https://linear.app/outfitter/issue/FOR-10) and the [pilot report](pilot-qualification.md) supply historical context at pilot source `5264279b9ce776d2a8f8e6c3785c663d9b653cf8`: assigned-human rules had regression coverage, but no live assigned-human approval scenario was exercised. The [reviewed initiative plan](https://linear.app/outfitter/document/ranger-implementation-and-forge-integration-plan-fe4ebca64ae0) explicitly separates this gap from Ranger integration. These records establish neither current worker availability nor live human-approval qualification.

## Proposed consumer and workflow

Propose a new private, content-free consumer named `outfitter-dev/forge-human-review-qualification`. This is a proposed identity, not a reservation, verified available name, or permission to create a repository. Matt must approve the owner/name, visibility, lifetime, and accountable operator. Use harmless text fixtures with no product code or private source. Choose this same-owner case first; it establishes no personal-account/private cross-owner distribution claim.

The proposed workflow is an operator-invoked, single-PR collection/evaluation on a disposable `qualification/base` branch. Create bounded fixture PRs against that branch, request individual human review, collect a stable baseline before asking for approval, let the named humans act through GitHub, then collect and evaluate again. Controlled fixture commits advance the PR head or disposable base for negative cases. Do not use a production default branch or a merge queue. No PR needs to merge to prove the human gate and eligibility decisions.

Use trusted synthetic passing lint/test/build and agent-review facts to isolate the live human boundary. Mark those facts and resulting receipts as fixtures: this is not qualification of real verification, agent review, end-to-end landing, or provider availability. The pass means GitHub human facts were authentically collected, normalized, and evaluated under the stated policy, with other gates held constant. No model call is required. A later full consumer qualification must replace fixture facts with separately qualified producers.

## Actor and assignment policy

| Role | Proposal and requirement before execution |
| --- | --- |
| Accountable owner/operator | Propose Matt; acceptance, backup, time budget, and permission to perform each fixture operation remain unconfirmed. |
| PR author | Select a distinct authorized actor, with an immutable GitHub user ID. The author cannot supply the required human self-approval. Agent-created author activity requires its own explicit permission. |
| Assigned human | Propose Matt (`galligan`), subject to his participation and repository access. Verify immutable user ID and human account type; do not infer these from a display name or possession of a token. |
| Voluntary objector | Select another consenting human with access and permission to request changes; this must be distinct from the assigned reviewer for the independent-objection case. |
| Landing-authorized actor / negative actor | Name the authorized actor IDs and a distinct consenting actor who may manipulate the test label but is excluded from landing authority. Repository write access alone is not this policy's landing grant. |
| Credential and evidence custodian | Name the person responsible for scoped access, expiry/renewal, private retained evidence, and final cleanup. This brief assigns no new credential or repository access. |

The proposed policy requires one named individual human once assigned. Its requirement persists after review submission or request removal. Current requested reviewers alone are insufficient. Avoid team requests in the passing scenario; an unsupported team requirement must block rather than disappear. Count only an effective approval bound to the exact repository, PR, head, and base. Comments do not erase an earlier approval; later changes requested or dismissal do. An unassigned approval cannot satisfy the assigned person's requirement. A voluntary outstanding objection blocks even after a push or base change and even if its original binding is unavailable. Dismissing an objection requires a separately authorized actor and does not satisfy an assigned approval requirement.

## Trusted collection and execution boundary

Run the collector and Forge CLI from an operator-approved immutable runtime outside all proposed checkouts. The initial source references are pilot `5264279b9ce776d2a8f8e6c3785c663d9b653cf8` for `machinery.collect_github` and its [gate contract](https://github.com/outfitter-dev/agentic-ci-pilot/blob/5264279b9ce776d2a8f8e6c3785c663d9b653cf8/docs/gate-contract.md), and Forge `e246c447105ef21bb027c7eae7b5f083eb39499d` for the evaluator/CLI. Freeze actual trusted revisions, dependencies, policy, and runtime digests in the later execution packet; these references do not install or qualify a runtime. Consumer code cannot choose the collector, policy, credentials, or trusted output channel and is not executed by this workflow.

Forge currently accepts normalized facts, not pilot JSON, and does not implement live collection or assignment persistence. A focused trusted normalization/fixture harness is therefore a prerequisite deliverable of the future execution task. Reuse the pilot's source-binding semantics and Forge's single evaluator rather than creating another decision engine. Qualify this bridge offline for original bindings, effective-review ordering, malformed/incomplete service reads, and protected state/output before using it live. Do not relabel an unbound old review with current SHAs. Shape validation and matching self-reported fingerprints do not authenticate a producer.

The collector must authenticate GitHub responses, verify repository and immutable actor identities, paginate complete review/request/timeline/thread data, preserve assignment history outside checkout cleanup, and select effective reviews by submission time. Record a stable head/base observation strictly before an approval's `submitted_at`. GitHub approval records do not supply the original base; missing, late, ambiguous, or changed observations leave the approval unbound. The pilot cannot reconstruct unobserved base movement between snapshots: keep the disposable base under the sole fixture operator's control, record every mutation, and state this limitation in the result. Retain qualified original bindings across later collections. Validate the trusted UTC clock and collection order; clock or ledger integrity uncertainty blocks the run.

Use complete stable collections before and after each intended human action, preserving the assignment ledger and raw authenticated references. Re-read safety inputs at collection end; mutation or incomplete pagination aborts collection without replacing the last good ledger. Missing/canceled/failed collection produces no fresh passing facts. Recollect before a hypothetical landing decision and report the collection window: this is not an atomic GitHub transaction or protection against subsequent mutation. Actual landing would still require hosted enforcement and separate authorization.

Keep credentials and ledger/output writable only by the trusted runtime/operator, outside proposed code and cleanup. Record original collector provenance and policy fingerprints; do not grant a credential to a fixture PR job. The operator must select and verify a protected local location, permissions, backup/restore behavior, retention duration, readers, and a minimized reporting destination. Sharing evidence via GitHub, Buildkite artifacts, or another store is an explicit data transfer decision. No transcript, token, or raw private ledger belongs in Git.

## Qualification matrix

Start each case from a recorded fixture state; change one input/action at a time and collect a new receipt. Keep the synthetic nonhuman gates passing unless the case specifically changes provenance. Inspect the structured `human-review` and `mergeability` decisions separately from overall eligibility.

| Case | Action and expected observation |
| --- | --- |
| Assigned approval passes | Record the request and stable baseline; the assigned human then approves unchanged head/base. Complete collection yields exact-bound approval, passing human gate, and eligibility only when all other explicit landing facts also pass. |
| Assignment history survives | Submit the review so the current request disappears, and separately remove a fresh request without approval. The persisted requirement remains; disappearance alone never waives approval. Removing the ledger/marking assignments uncollected blocks. |
| Wrong or absent reviewer | No approval, approval by another human, an unresolved team request, or attempted self-approval cannot satisfy the selected individual requirement. Capture any GitHub rejection as a service outcome, never fabricate a human approval. |
| Head changes | After valid approval, advance only the fixture head. Old approval blocks; a new stable baseline followed by a new assigned approval is required to restore the human pass. |
| Base changes | Advance only the disposable base with head unchanged. The recorded old-base approval blocks. Restore via fresh baseline and subsequent approval, not by rewriting its original binding. |
| No trustworthy prior base | First observe an existing approval with no prior baseline; also inject baseline-at/after-submission, invalid timestamp, and unknown-clock cases offline. Approval remains unbound and cannot pass. Distinguish offline fault injection from actions actually performed on GitHub. |
| Comment and dismissal | A comment-only review after approval preserves it; an authorized dismissal of that approval leaves the assigned requirement unsatisfied. A later changes request also blocks. Order by submission time, not creation ID. |
| Voluntary objection | A distinct unassigned human requests changes. It blocks despite the assigned approval, a new head/base, or an unavailable objection binding. A later effective approval or authorized dismissal removes that objection, while the assigned requirement remains independent. |
| Authorization actor | Apply the selected test landing label through the consenting actor excluded from authority. Human review may remain passing, but trusted `mergeAuthorized` is false and eligibility blocks. A label by itself, bot display name, or arbitrary JSON cannot grant landing. |
| Incomplete or substituted evidence | Offline harness faults include wrong repository/PR, stale runtime fingerprint, duplicate effective reviews, missing pages, canceled collection, malformed response, tampered ledger, and consumer-written output. Reject at the authenticated collector boundary or block/return invalid at the evaluator as appropriate; never accept a forged normalized pass as authenticated evidence. |
| Mutable collection | Change a fixture safety input during the collection window in a controlled fault case. Abort without overwriting good state; collect afresh after stabilization. No merge action is used to test this. |

Live cases need actual consenting participants; an agent cannot manufacture a person's approval, request-changes judgment, dismissal authority, or participation. Some ordering/clock/malformed-service cases are deliberately offline; report coverage by mechanism and do not count those as live GitHub outcomes. Merge-group/member admission and simultaneous-queue behavior remain FOR-11's separate gap.

## Access, operations, evidence, and cleanup

The future packet must confirm GitHub service availability; repository creation and fixture-write authority; review/request/timeline/thread read access; permission to request/remove reviewers; consenting humans' review access; and any label/dismissal permissions used by selected cases. Select the minimum supported credential scopes for those exact operations and repository, with expiry/renewal and custodian recorded without secret values. Confirm trusted source access separately; same owner does not automatically supply it. No Buildkite, model, Ranger, production worker, package registry, or new organization-wide permission is required by this proposed workflow.

Permitted future operations must be enumerated and authorized before execution: create the selected disposable consumer if approved, write only its fixture branches, open/close fixture PRs, request/remove named reviewers, collect service facts, and let named humans submit the selected reviews. Add test-label changes and dismissal only if their actors/permissions are explicitly accepted. Proposed limits: one open fixture PR at a time, one recorded attempt per case plus one explicitly explained repair attempt, and a named time/access budget approved by the operator. There is no default permission to merge, enqueue, publish, alter default-branch/ruleset settings, create tokens, or expand access.

For every case retain: case ID and expected result; repository ID/PR; before/after head/base; trusted source/runtime/policy/fixture digests; collector run and collection timestamps; assignment-ledger integrity reference; service review/timeline IDs, human actor IDs and `submitted_at`; original approval binding or explicit unbound reason; request/removal/objection history; completeness/fault disposition; normalized input; actual six gate decisions/reason codes and CLI exit; and a minimized evidence receipt. Review expected versus actual with the named human/operator. A case passes only when its specified positive or negative result is observed. Unknown, unavailable, or unexecuted cases stay explicit; one passing approval cannot close the matrix.

On failure, stop mutations, preserve partial evidence, and leave no eligibility claim from an incomplete run. Cleanup closes fixture PRs and removes only approved disposable branches/resources after checking identities and current state. Record what remains and why. Preserve private evidence/ledger for the approved retention period, then have its custodian delete the designated fixture records and revoke/retire test-only access as authorized. Never erase historical pilot state or shared credentials. Do not delete a whole repository or restore settings over concurrent work without an explicit owner-approved cleanup operation. Because no production path is changed, rollback is stopping the disposable workflow and preserving evidence; it is not a worker restart or consumer migration.

# Strict release version and channel assessment

`evaluateReleaseVersion(input, policy)` assesses literal previous/next versions and a requested destination tag, without filesystem, provider, registry, publishing or tag effects. It adapts the channel mapping and first-differing-core comparison in [release-action's version helper](https://github.com/outfitter-dev/release-action/blob/781379183eaf3d4b6139894582e58a47cad28e08/src/version.ts) and [16 source tests](https://github.com/outfitter-dev/release-action/blob/781379183eaf3d4b6139894582e58a47cad28e08/src/version.test.ts). This Forge-only FOR-19 slice deliberately replaces permissive fallback behavior; it does not adopt a product or implement its versioning workflow.

## Product policy and result

`ReleaseVersionInput` supplies `previousVersion`, `version` and `tag`. Trusted `ReleaseVersionPolicy` supplies `stableTag` and `prereleaseTags: [{identifier, tag}]`. There are no default destinations. A stable next version requires exactly the declared stable tag; a prerelease requires an exact mapping for its first identifier. Unknown/case-mismatched/numeric channels block. Several identifiers may share one prerelease tag, but identifiers cannot repeat and no prerelease may target the stable tag. The previous version only needs valid syntax: historical channels need not remain in the current destination policy.

This first contract supports lowercase word/hyphen selectors (`stable`, `preview`, `release-candidate`), at most 64 characters, and at most 100 prerelease mappings. The wildcard `x`, digits, periods, ranges, whitespace and other selector forms are unsupported rather than normalized. An empty mapping list deliberately allows stable releases only. Products requiring a different vocabulary need a separately qualified contract; this is not a general npm tag parser or proof of installed registry permissions. Unknown fields, malformed records and sparse/duplicate mapping entries block.

A passing result reports `change`: `major`, `minor` or `patch` for the first changed core component, otherwise `prerelease` for increasing prerelease precedence or `finalization` for the same core graduating to stable. The source classified both last cases as patch; Forge exposes the distinction so product policy decides their release intent. There is no inferred `release:*` label, lockstep/independent package policy, permitted transition graph or required bump size. Cross-channel prerelease progression is considered newer only according to SemVer precedence; a product must separately restrict any disallowed channel transitions.

Results return `decision`, nullable `change`, diagnostics and a binding containing the exact literal inputs plus `releaseVersionPolicyDigest(policy)`. Canonical object keys make separately constructed equal policies interoperable; array order remains bound. Invalid input/policy returns a null binding; any blocked assessment returns a null change. A binding on a blocked result describes the attempted input, not a successful assessment.

## Strict versions and metadata

Both versions must be complete, unprefixed ASCII SemVer strings of at most 256 characters. Core components and purely numeric prerelease identifiers must have no leading zeros and must fit JavaScript's nonnegative safe-integer range. Identifiers use only ASCII letters, digits and hyphens; empty identifiers, malformed separators, whitespace, `v`/`=` prefixes, shortened versions and unsupported numeric magnitudes block. Build metadata may contain numeric identifiers with leading zeros, as SemVer allows. Unsupported input cannot become a stable release or an inferred `next` channel.

Valid build metadata is preserved in the literal binding and ignored for precedence/channel selection. Thus `1.2.4-beta.2+build.7` still requires the product's beta destination, and changing only metadata (`1.2.3+one` → `1.2.3+two`) does not establish a newer version. A stable version with valid metadata uses the explicitly declared stable tag. Malformed metadata blocks in both previous and next versions. Products may impose additional restrictions on metadata or artifact/version association; this helper grants no registry publication eligibility.

Syntax is checked before using the existing pinned Bun 1.4.4 [`semver.order`](https://github.com/oven-sh/bun/blob/main/docs/runtime/semver.mdx) primitive for precedence. Bun comparison accepts some noncanonical forms, so it is not used as the validator. Comparator failures block. Offline tests qualify numeric prerelease ordering, prefix ordering, stable/prerelease precedence, metadata equivalence and supported numeric boundaries on the pinned runtime. No new dependency or alternate comparator is introduced.

## Trust and qualification limits

The function computes from supplied strings; it does not collect or authenticate an old version, a manifest, a repository, a release head, an artifact or a registry observation. Its literal-input binding is not a revision-bound evidence receipt. A trusted collector must establish those associations, choose policy outside the proposal and attach the result to the correct product/subject before normalizing it into a named [release-policy](release-policy.md) assessment. Stamping current revisions onto unrelated version strings cannot establish that association. The [generated-release diff check](generated-release-diff.md) proves file roles only; this function alone does not prove those files contain these versions or valid changelog/changeset content.

Offline tests adapt source behavior while preserving deliberate differences: invalid versions never fall back to stable, degenerate prereleases never default to `next`, prereleases with metadata retain their channel, metadata alone never advances precedence, and finalization is distinct from a core patch. Negative cases cover malformed previous/next versions, unsupported channels, wrong destinations, equal/older versions, unsafe numeric magnitudes, invalid/ambiguous policy and immutable/canonical input behavior. Run `bun install --frozen-lockfile` and `bun run check`.

Current FOR-19 remains open for trusted product assessment collection, concrete version/channel/transition policy and consumer qualification through Forge commands. A public Actions adapter is optional only for a concrete consumer need; its source/access/runtime/bundle checks apply if selected, not as CLI delivery prerequisites. No live publish, tag change, cross-repo adoption, credential expansion or worker operation is included.

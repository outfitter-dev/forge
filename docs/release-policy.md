# Pure release-policy routing

This is the first Forge-only implementation slice of [FOR-19](https://linear.app/outfitter/issue/FOR-19), following the accepted [canonical pattern map](ci-release-patterns.md). `evaluateReleasePolicy(subject, policy, evidence)` adapts the existing [release-action classifier at 7813791](https://github.com/outfitter-dev/release-action/blob/781379183eaf3d4b6139894582e58a47cad28e08/src/policy.ts) and its branch fixtures: block conflicting/unknown intent, require an audit reason for `publish:none`, default to manual intent, and allow auto only when its explicit conditions pass. It is a pure intent router and requirement accountant, not the entire upstream publisher or a new execution framework.

Product-specific version/diff/changelog/identity/stack assessments remain named, normalized check inputs. Forge does not implement a new package graph, choose a product's versioning rules, infer commands or copy the source repository's organization/bot identities. The fixture policy uses `example/release-fixture`; it is not a selected production consumer. The monorepo has been recommended as a possible future consumer, but no cross-repo implementation or adoption is released by this slice.

## Inputs and binding

The trusted caller supplies the expected `ReleaseSubject`: repository, branch ref, source commit, trusted workflow commit, validator commit, runtime identity, staged artifact SHA-512 integrity, version and tag. The three commits are explicit immutable 40-hex identities. Artifact integrity is canonical SHA-512 SRI. Actual evidence must match every subject field and the exact `releasePolicyDigest(policy)` SHA-256 of the consumer policy with recursively sorted object keys and preserved array order. Independently constructed objects with the same values and array order share a digest; changing an ordered check/channel list remains a policy change. A different workflow/source/validator/runtime/artifact/version/tag or policy blocks; a current label cannot refresh old evidence.

The product policy explicitly supplies its repository/ref, supported channel-label/tag pairs and each channel's automatic eligibility, allowed `release:*` labels, required safety-check IDs, separate auto-only check IDs, and required CI check names/producers. No organization, runtime, protected environment, actor, channel or check is inherited from Forge. Required and auto-only sets cannot overlap. Lists are bounded to 100 entries; selectors/IDs are bounded, JSON-shaped values. CI names may contain spaces. Unsupported policy/evidence fields and malformed/sparse/duplicate observations fail closed.

Evidence carries version-PR intent labels, an optional normalized no-publish audit reason, publication state, named product check outcomes and CI proof. The collector must establish the version PR and source/check association before normalization; this operation does not parse/authenticate GitHub bodies or invent source-PR stack membership. Unknown or conflicting `publish:*`, configured `channel:*` and `release:*` intent blocks. Unrelated labels have no routing meaning. The fixed publish verbs are `publish:auto`, `publish:manual`, `publish:none` and `publish:block`; product label vocabularies beyond this contract need a separately qualified extension.

## Decision ordering

1. Validate inputs, exact subject/policy binding, repository/ref and supported tag. Invalid or stale data blocks; invalid policy/expected subject emits no usable binding.
2. Block conflicting/unknown intent, explicitly blocked publication, unexpected check IDs, publication conflicts/partial/unavailable observations, and a selected channel/tag mismatch.
3. `publish:none` requires a normalized nonempty audit reason and returns `none`. No publication or release progression is eligible through this branch, so it may omit safety/CI execution; malformed or ambiguous supplied observations still block. Raw reason text is not retained.
4. For all remaining manual/auto paths, every product-declared required safety check and every required CI run must pass. Missing, failed, canceled, skipped, incomplete or unsupported required evidence blocks even an explicit manual request.
5. Missing publish intent or `publish:manual` returns manual eligibility after those safety requirements. It is not evidence that approval happened.
6. `publish:auto` additionally requires a configured auto-eligible selected channel and all declared auto-only checks to pass. Missing/non-passing auto-only evidence excludes automation and routes to manual; it never waives a safety requirement. Otherwise the result is `auto`.

The manual/auto distinction faithfully retains the source router's low-risk fallback. A deliberate strengthening is that required safety and exact-head CI failures are blockers for manual as well as auto eligibility: upstream's simple auto-to-manual CI fallback is not copied as an approval bypass. Product policy must put anything that approval cannot waive in `requiredChecks`; `autoChecks` are only conditions for automation. Model output cannot add fields or override deterministic blockers.

Publication state is supplied by trusted complete collection: `unpublished`, `complete`, `partial`, `conflict` or `unavailable`. Partial/conflicting/unavailable evidence blocks, including an attempted skip. `unpublished` describes the collector's observation, not proof that an immutable version is free; delayed visibility and occupied-version recovery remain [FOR-18](npm-evidence.md). `complete` does not tell a caller to republish. Do not map an incomplete registry response or a subset of a coordinated package set into fabricated completeness or a safe retry. Publication ordering, recovery and mutation remain outside this router.

## Exact-head CI and qualification limits

This first slice accepts only `proof: "exact-sha"` with `testedSha === subject.sourceSha`. It requires each configured name/producer pair exactly once with a nonempty execution ID and passed state. Duplicate name/producer observations or reused producer/execution IDs are ambiguous and invalid. Runs from another producer, commit or proof mode cannot supply missing required CI. Other unrelated check names do not satisfy or erase required runs.

The type preserves `release-pr-head` and `assumed` as recognizable inputs so they return an explicit unsupported-proof blocker rather than being silently normalized to passed CI. Trails' tree-bound alternate proof in the accepted map is **not implemented or authorized** here. Supporting it requires a concrete consumer policy, authenticated collection of the actual relationship/tree facts and offline negative tests before adoption. There is no `ciPassed` escape hatch.

**Shape and binding are not producer authentication.** Check state, producer labels, execution IDs, source identity, audit reason and registry observations are trusted normalized inputs. The caller/collector must establish their authenticity, completeness and exact association, including product check implementation and required artifact evidence. Merely stamping the expected subject around an old result does not make it current. [FOR-24](package-artifact-validation.md) and FOR-18 retain their own artifact/registry limitations; an adapter must preserve those distinctions rather than turn any JSON response into a passing safety check.

Results contain only decision, known binding, blockers, auto diagnostics and stable reason codes/declared IDs. They omit raw process/provider output, audit text and arbitrary unknown fields. There is deliberately no `shouldPublish`, `createGitHubRelease`, approval executor or command callback: routing cannot grant publish/tag/release authority. A separately authorized action must enforce current requirements again at its boundary.

## Offline coverage and remaining FOR-19 scope

The credential-free suites adapt the source classifier's branch scenarios and cover product-controlled channels, every required/auto-only/CI failure state, exact binding changes, unsupported CI proof, missing/wrong/duplicate runs, stale policy, conflicting/unknown/repeated labels, audited skips, partial/conflicting/unavailable publication, malformed and unsupported inputs, unknown overrides and additional product safety requirements. The fixture declares artifact/release-context requirements and generated-diff/version-delta/stack auto checks; their passed observations are synthetic, not product qualification or signature verification.

Run `bun install --frozen-lockfile` and `bun run check`. No provider, registry request, filesystem/process runner, credentials, protected-environment approval, package publication, product migration, Actions edit or worker operation is included. Current FOR-19 remains open for Forge release-command integration, trusted product assessment collection and concrete policy/consumer qualification. The CLI is primary; additional proof modes need a concrete product requirement, and a public Actions adapter is optional. If a consumer selects an adapter, qualify its immutable source/access/runtime/bundle contract before adoption; those checks are not CLI delivery prerequisites. FOR-20 preserves existing Actions consumers, FOR-21 maps useful capabilities to subsume, and FOR-23 sequences later monorepo command adoption after Forge self-consumption and selected outside consumers. Existing product paths stay operational; the parked tokens trial remains parked.
